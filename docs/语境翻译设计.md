# 语境感知翻译设计（MVP）

> 目标案例：日语「返信（へんしん）」被识别/翻译成「变身」。
> 同音词（返信/変身）单句无法区分，需要借用上下文。

## 1. 问题拆成两层

| 层 | 现状 | 失败原因 | 本方案 |
| --- | --- | --- | --- |
| 识别 | Whisper 逐段解码 | 每次只看 0.2~4 秒音频，没有对话记忆，同音汉字只能按声学概率猜 | 滑动上下文 + 同音词后处理纠正（有线索才改） |
| 翻译 | 逐句送机翻 | 单句没有指代/场景信息；LLM 通道也不知道前文 | 最近几条原文/译文 + 术语表注入 LLM 通道；免费通道保持单句 |

## 2. 识别层

### 2.1 不用 initial_prompt 做上下文（明确取舍）

`core/asr.py` 顶部已有实测记录：把词表/提示词交给解码器时，Whisper 会把提示词
当正文复述（`prompt_echo` 护栏就是为此加的，见 asr.py 的“绝不再用 initial_prompt
传热词”）。把「最近三句」塞进 `initial_prompt` 等于把复述风险从“词表”扩大到
“整段对话”，一旦模型在静音/噪声段补全上下文，字幕会出现原文里根本没说的话。

因此 MVP：**上下文不进解码器**，只用于解码之后的确定性纠正。代价是同音词命中率
依赖规则表，而不是模型；收益是零幻觉、零额外解码耗时、可开关可观察。

### 2.2 滑动上下文 + 同音词纠正

数据结构（`core/context.py`）：

```python
@dataclass
class Turn:
    src: str      # 上屏的原文（已纠正）
    tgt: str      # 译文（可能为空）

class ContextBuffer:
    _turns: deque  # maxlen=8，实际使用条数由 cfg.context_window 决定
```

规则表（只收高置信度、低误伤的几对）：

```python
{"wrong": "変身", "right": "返信",
 "cues":   ("メール", "LINE", "返事", "連絡", "メッセージ", "DM", "既読", "送る"),
 "guards": ("姿", "魔法", "ヒーロー", "ベルト", "チェンジ", "スーツ")}
```

判定：当前句含 `wrong`，且「当前句 + 最近 N 句」里出现任一 `cue`，且当前句没有任何
`guard` → 替换为 `right`；否则原样保留。另有一条结构化护栏：整句只剩这个词加标点
（「変身！」「変身!!」）时不改——感叹句几乎都是字面意思。每次替换都通过状态栏输出
`语境纠错：変身→返信（线索：メール）`，便于用户发现“改得更错”并关闭开关。

首批规则只收 2 对：`変身→返信`、`対照→対象`。像 `機能/昨日`、`機関/期間` 这种两边
都常用的同音词**不收**——线索词很容易误命中，改错比不改更糟（实测构造例：
上一句含「今日」、当前句「機能を使ってた」会被误改）。规则表内置，
不开放用户编辑（用户已有 `word_map` / `name_roster` 两套自定义纠错，避免第三套入口）。

### 2.3 接入点

- `core/pipeline.py` `_asr_loop`：`transcribe()` 之后、`on_partial()` 之前
  （当前行号约 457-487）。纠正后的文本才上屏、才送翻译。
- 上下文在 `_flush_ordered()` 按上屏顺序 `push(disp_text, out)`，保证并行翻译
  回包乱序也不会把上下文顺序打乱。
- `start()` / `stop()` 清空上下文，避免上一场直播的句子污染新一场。

## 3. 翻译层

### 3.1 LLM 通道注入上下文

只对 `custom`（OpenAI 兼容 / DeepSeek）生效，因为只有它能接受 system prompt。
每次请求的 system 消息追加：

```
最近的对话（仅供理解语境，不要翻译、不要复述）：
原文：…
译文：…
…
术语表（当前句出现时按此译法）：
原词→译法
只翻译用户消息里的当前句，不要补全、不要解释。
```

- 上下文最多 `cfg.context_window` 条（默认 3），每对截断到 200 字，整块上限 600 字。
- 译文为空的历史条目不注入。
- 术语表来自 `cfg.context_glossary`（多行 `原词=译法`），缺省为空。
- 缓存 key 从 `text` 变成 `(text, 上下文指纹)`，否则同一句在不同语境下会命中旧译文。
- 上下文污染护栏：带上下文时若译文长度 > max(60 字, 原文 3 倍)，判定为把前文一起翻了，
  本次译文丢弃、只显示原文。
- 译文兜底：原文已认对「返信」但译文仍出现「变身」时，按固定映射改回「回复」并写日志
  （与 `enable_homophone_fix` 共用开关）。

### 3.2 免费通道（腾讯/彩云/Edge/Google/DeepL…）

这些接口没有上下文参数，**默认仍保持单句行为不变**（不拼接前文，避免把前文翻出来
混进字幕，也避免延迟上升）。识别层的同音词纠正对所有通道生效，这是本方案对
「返信」案例的主要修复；翻译层上下文是配了 API Key 后的增益项。

可选的试验开关 `enable_free_context`（默认 `false`）打开后：

- **极短前缀**：只取最近一句非空原文，压成一行、截到 60 字
  （`core/context.format_free_context`），用 `\n` 拼在当前句前面送翻。
  取 60 字而不是整段的理由：前缀越长，「整段一起翻/改写」的概率和延迟增量越大。
- **明确分隔**：前缀与当前句之间用换行分隔，译文一般会保留换行。
- **只认结构化分段**：`_split_free_segment()` 要求译文至少两段，取最后一段
  作为当前句；**只有一段时视为切不开，绝不猜句子边界**（猜错会把上一句译文顶到当前字幕上）。
- **异常丢弃 + 回退单句**：切不开或最后一段长度 > `max(60, 原文×3)` 视为污染，
  在剩余预算内用干净单句**重发一次**；重发失败则换下一个通道，全失败则只显示原文。
- **缓存 key 区分**：带语境时 key 为 `(text, "free", 前缀)`，与不带语境的 `text`
  互不命中，避免同一句在两种模式下串味。
- **延迟**：每次请求多带 ≤60 字；最坏情况（分段失败）多一次请求，仍受
  `Translator.BUDGET`（5 秒）总预算约束；开关关闭时**零额外请求、零额外延迟**。
- **已知风险**：免费通道没有「只翻译最后一句」的指令能力，个别引擎会把两句合成
  一句话或改写语气；护栏只能保证不把上一句译文上屏，**不能保证这一句的质量一定变好**。
  收益主要体现在省略主语/指代（「それ」「あれ」）这类句子；是否划算建议按 §8 对比。

## 4. 延迟预算

| 环节 | 增加量 | 说明 |
| --- | --- | --- |
| 同音词纠正 | < 0.5 ms/句 | 4 条规则 × 几次 `in` 判断 |
| 上下文入 prompt | +50~150 token，约 0~80 ms | 仅 custom 通道；免费通道 0 |
| 免费通道前缀 | 每次 +≤60 字 | 仅 `enable_free_context=true`；分段失败时最坏多一次请求（仍受 5 秒总预算） |
| 额外网络请求 | 0 | 默认配置不新增调用、不新增线程 |

总预算仍在原有 `Translator.BUDGET` 之内；免费通道端到端延迟不变。

## 5. 风险与回退

| 风险 | 处理 |
| --- | --- |
| 纠错改得更错 | 必须同时满足“含错形 + 有线索 + 无反向线索”；默认只收 4 对；每次改动打到状态栏；`enable_homophone_fix=False` 一键关闭 |
| 提示词污染/复述 | 上下文只进翻译请求的 system 消息，不进 Whisper；明确要求“只翻译当前句”；整块限 600 字 |
| 上下文过长拖慢/指代错乱 | 默认 3 条、单条 200 字、整块 600 字；`context_window=0` 等价关闭 |
| 翻译错乱（LLM 把上下文一起翻出来） | 若输出长度明显超过输入（> 3 倍且 > 60 字），本次译文丢弃，只显示原文 |
| 上下文不可用 | 冷启动/刚清空时 `snapshot()` 为空，`translate()` 走原单句路径，行为与现在完全一致 |
| 规则与用户 `word_map` 冲突 | 顺序：ASR `word_map` → 语境纠错；语境纠错只处理规则表内的词，不碰用户词表 |
| 免费通道把两句话合成一句 | 只认换行分段；切不开即判定污染，回退单句重发一次，失败则只显示原文 |
| 免费通道只翻了后半句 | 取最后一段恰好对应当前句；无法验证语义时宁可回退，不拼上一句译文 |
| 免费前缀导致延迟上升 | 前缀 ≤60 字；总预算仍是 5 秒；默认关闭，关闭时路径与改动前完全一致 |

## 6. 配置项（config.json）

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `enable_context` | `true` | 翻译层上下文总开关（关闭后 custom 通道也按单句翻） |
| `context_window` | `3` | 上下文条数，0~8 |
| `enable_homophone_fix` | `true` | 识别层同音词纠正总开关 |
| `enable_free_context` | `false` | 免费通道也带语境（上一句原文作 ≤60 字前缀），试验项 |
| `context_glossary` | `""` | 术语表，多行 `原词=译法`，仅 custom 通道使用 |

面板已提供「语境辅助」组（位置：翻译组之后、断句灵敏度之前），改动即存：

| 控件 | 对应配置 | 说明 |
| --- | --- | --- |
| 勾选「翻译参考前文」 | `enable_context` | 关闭时前文条数与免费语境一并置灰 |
| 「前文条数」0~8 | `context_window` | 与勾选同一回调写盘 |
| 勾选「识别同音词纠正」 | `enable_homophone_fix` | 每句重读配置，无需重启 |
| 勾选「免费通道也带语境（试验）」 | `enable_free_context` | 默认不勾 |
| 多行「术语表」 | `context_glossary` | 停顿 600ms 保存；关窗时补存未落盘内容 |

所有回调都在 GUI 线程内直接写 `cfg` 并调用 `cfg.save()`（内部自带写锁 + 原子替换），
不跨线程碰控件，也不通知控制器——翻译/识别层每句重新读取配置。

## 7. 落地范围

- 新增 `core/context.py`：`ContextBuffer`、`fix_homophones()`、`format_context()`、
  `format_free_context()`。
- `core/pipeline.py`：接入纠正、上下文收集、翻译传参、启动/停止清空。
- `core/translator.py`：`translate(text, context=())`，custom 通道注入上下文与术语表，
  缓存 key 带上下文指纹，输出长度异常时丢弃译文；免费通道可选前缀 + 分段护栏。
- `core/config.py`：五个配置字段 + 校验（含 `enable_free_context`）。
- `ui/panel.py`：「语境辅助」组（四个开关/旋钮 + 术语表），改动即存。
- 不做：Whisper `initial_prompt` 上下文、跨场次持久上下文、免费通道强制术语。

## 8. 验证方法

离线（不需要麦克风）：

```powershell
.\.runtime\venv\Scripts\python.exe -c "from core.context import fix_homophones; print(fix_homophones('変身してなかった？', ['メール来てたよ']))"
# 期望：('返信してなかった？', ['変身→返信（线索：メール）'])
```

实测（聊天语境）：

1. 在聊天/LINE 语境的日语音频里说「返信」；
2. 状态栏出现 `语境纠错：変身→返信（线索：…）` 即规则命中；
3. 字幕原文显示「返信」，译文为「回复」类；
4. 说「変身！」（变身）时不应被改，日志里也不应出现纠错行；
5. 把 `enable_homophone_fix` 改成 `false` 重启，同一句不再纠正——用于对照。

回归：不配 API Key 时翻译延迟与改动前一致（免费通道代码路径未变——`enable_free_context`
默认关闭时既不拼前缀、也不多请求）。

免费语境对比（同一段录播、同一通道）：

1. 面板「语境辅助」里不勾「免费通道也带语境」，跑一段含「それ」「あれ」的对话，记下字幕；
2. 勾上后再跑同一段，逐句对比主语/指代是否更明确；
3. 观察日志是否出现 `免费语境分段失败，回退单句`——出现频率高说明该通道不保留换行，
   这类通道开这个开关基本只有额外开销，建议关掉；
4. 想量化延迟：看「通道健康检查」的耗时，或用调试模式日志里的单句请求耗时对比。
